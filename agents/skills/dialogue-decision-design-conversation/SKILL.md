# Dialogue Decision Design Conversation

Help the user make the decisions that are actually theirs. Keep an internal decision ledger with each item's question, status (open, tentative, decided, or revisited), chosen answer, rationale if material, and dependencies. Derive the initial inventory from the request and available evidence; add or remove items as the conversation reveals what matters. Do not treat a recommendation or an unanswered question as a decision.

Keep a running, rough estimate of the percentage of decision work settled for the current topic, separate from implementation progress. When establishing the estimate, assign each known open decision an approximate share of the remaining work. **Before posing each question, record how many percentage points settling it is expected to earn**; reserve part of its share for foreseeable follow-up decisions rather than counting the whole topic as settled too early. When the user answers, advance the estimate by the share actually resolved and carry any unresolved share forward. Recalculate the baseline only when new evidence materially expands, removes, or reshapes the remaining work, or makes the old estimate misleading; explain a visible downward reset. Mark the estimate approximate, but do not repeat an unchanged rounded percentage after meaningful decisions merely because the original rounding concealed progress. Whenever posing new decision questions, print an unnumbered `Progress: ~X% done` line before `Next:`; “done” means decision work, not implementation.

Always start a new planning discussion with **three questions**. Continue asking until every decision needed for implementation is settled. In later rounds, use three questions while enough substantive independent decisions remain, or follow a different pace explicitly requested by the user. Fill each batch with independent open decisions, preferring upstream ones. A question that may lead to follow-ups does not shrink the batch by itself: ask it alongside other independent items. Use fewer questions in later rounds only when there are not enough substantive independent decisions, or the upstream answer could materially change every remaining candidate.

Before posing each decision as a question, give one sentence or a short paragraph of context explaining the problem it addresses. Number the questions (1, 2, 3), even when presenting only one, and label each question's two or three options with letters (a, b, c) so the user can refer to an answer such as “2.b.” State each option's main tradeoff and mark one recommendation with its reason. Avoid a long context dump or a full option matrix; let the user ask follow-up questions and go deeper only where they want. Do not append a generic “What do you think?” after the options or mention the skill in the dialogue.

If the user asks a question, answer it directly and briefly before returning to the current decision. If they propose another option, evaluate it rather than forcing the original menu. If their answer is ambiguous, ask a focused clarification for that item while retaining other independent questions in the requested batch. Never silently choose for them; an explicit “use your recommendation” does count as a decision.

After each choice, update the ledger without conversational recaps such as `Decided: ...` or `Settled: ...`. Focus on what needs deciding next. Revisit an accepted choice only when an unaddressed issue or changed circumstances warrants reconsideration, explaining that specific reason. Carry forward unanswered questions and add independent ones to preserve the requested batch size; use fewer only when no suitable independent questions remain or an upstream answer could change every remaining candidate. Introduce the next batch with an unnumbered `Next: ...` line; omit it when no relevant decisions remain. Reserve numbered items for questions and lettered items for options. Follow root `AGENTS.md` for decision-record ownership and retain open proposals in task-local notes unless the user explicitly requests another destination.

When all relevant decisions are settled, state the next step and any remaining uncertainty without repeating the choices. Give a retrospective summary only when requested. Do not turn the conversation into implementation or a broad plan unless the user asks for that next step.
